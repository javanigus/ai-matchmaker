- Separately, the high-frequency per-turn chat/extraction path itself moved from `gpt-4o-mini` to `deepseek/deepseek-v4-flash` (~7x higher Intelligence Index, cheaper). Its benchmark throughput looked faster too (103.7 vs 93.9 tok/s), but real timed onboarding turns disagreed: `gpt-4o-mini` averaged a tight, consistent ~5s/turn across 5 samples; DeepSeek V4 Flash averaged ~10.8s and ranged 6.9–14.8s — benchmark tok/s doesn't reliably predict real end-to-end latency through OpenRouter's routing for a given model/provider path. Founder chose to keep DeepSeek V4 Flash anyway, intelligence over the latency gap, after seeing both real comparisons side by side. Also considered and rejected Kimi K3 at low reasoning effort for this path — same intelligence ballpark as DeepSeek V4 Flash per its own benchmark, but 3x slower to generate and ~78x pricier per output token, so not worth even a real timed test.
- Per founder request, each category's interview question is now a deterministic two-step sequence rather than one open-ended ask: a quick, easy first question (for the 4 categories with a real quick_fact list — Relationship Goals, Family, Religion & Spirituality, Career — this lists the actual canonical options verbatim, which also fixed a pre-existing mismatch where the model was paraphrasing its own made-up options instead of the real enum), then one open-ended follow-up once *any* signal exists for that category, building on what's already known instead of repeating the closed question. Which step applies is decided in code from whether `pending_confidence`/`confidence` already exists for the focus category — not left to the model to track across turns, for the same reliability reason `focusCategory` itself is code-driven.
  - First real-browser test caught a genuine gap this session's own verification missed: a bare, explicit closed-pick answer ("marriage") got High confidence immediately (correctly, per confidence's own rules — an unambiguous statement *is* High confidence right away), which meant the category counted as "met" and advanced before the guaranteed open-ended follow-up ever ran — exactly the "replaced a web form with chat that does the same thing slower" experience the founder was watching for. Root cause: confidence measures certainty about what was captured, not how much was captured. Fixed by requiring genuine narrative depth (a word-count floor on the actual stored text) in addition to Medium+ confidence before a category counts as done — `meetsBaseline()`, used everywhere (pills, progress %, `baseline_reached_at`), not just the question-selection logic.
  - That fix immediately surfaced a second real issue: extraction was padding a bare pick into a fuller-sounding paragraph by reusing the question's own wording ("marriage" → "I'm not interested in anything casual or short-term; I want a serious relationship that leads to marriage"), which cleared the new word-count floor without the user having said anything more. Fixed the actual root cause in the extraction prompt: never invent elaboration or reasoning the user didn't give, including by echoing the question's own phrasing back as if it were their answer — an honest bare-pick summary should say plainly that no further detail was given yet, not read as a fuller explanation. Verified clean end to end afterward: a bare pick correctly stays on the same category and asks an open follow-up; real elaboration afterward correctly advances with a genuine, evidence-backed summary and the right quick_fact.
  - The padding prompt fix didn't generalize, though — the same trick recurred on a different category ("balanced" for Lifestyle padded into "not a total homebody, not always out and about," reusing the closed question's own option words). Since the stored summary's wording is something the model controls (and can inflate), any check purely on that text was never going to be fully reliable. Fixed with a second, harder-to-game signal: a category updated this turn from a raw user message under 6 words is never trusted as narratively deep this turn, regardless of how the stored summary reads — it gets a real chance to build depth over more turns via the guaranteed follow-up instead. The user's own literal input length isn't something extraction can pad.
  - Lifestyle and Social Energy joined the four categories that already had a quick_fact (Relationship Goals, Family, Religion & Spirituality, Career) — Lifestyle: Mostly homebody / Balanced / Mostly outgoing; Social Energy: Mostly introverted / Slightly introverted / Balanced / Slightly extroverted / Mostly extroverted (`prd.md` updated). Fixed by giving every baseline category a real one-line description in the extraction prompt (not just its name), explicitly calling out Lifestyle vs. Social Energy as the two categories most likely to be confused for each other and stating what each is not about. Verified clean afterward: the same previously-contaminating message no longer produces any Social Energy row at all.
  - Per founder request, the closed-choice first question now comes with real tappable option chips instead of requiring the user to type a canonical value back out — faster for the user, and removes any typo/paraphrase for extraction to misinterpret. The API returns the exact option list as `quickReplyOptions` whenever the current turn is a step-1 question (`null` otherwise — verified both cases via curl); the onboarding page renders them as chips under the assistant's message, tapping one sends it exactly like typing it would. ## Deviations from the plan

- **Email confirmation is disabled** (`enable_confirmations = false`, pushed via `supabase config push` from `supabase/config.toml`). This was a dev-testing fix, not a product decision: the founder's real-browser signup attempt hit Supabase's built-in email rate limit (partly because a prior API-level test in this same session had already sent one). Disabling confirmation avoids sending any email at all during this phase, sidestepping the rate limit entirely rather than reaching for a second email vendor (Resend) this early, matching `PLAN.md`'s "one vendor until there's a real reason" stance. **Must be re-enabled before real users can sign up** — right now anyone can create an account with any email address, verified or not. `supabase config push` also synced two unrelated cosmetic settings from the default `config.toml` (MFA TOTP enroll/verify disabled, an `https://127.0.0.1:3000` redirect URL added) — harmless, not cleaned up, since pushing the config file syncs its whole state, not just the one setting that mattered here.
