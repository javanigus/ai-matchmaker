- Five real bugs found via the founder's own browser testing, all fixed: (1) confidence "flip-flopping" between turns — the extraction prompt showed category text but not its current confidence, so the model had no signal an established category shouldn't regress; fixed by showing `[current confidence: X]` per category with an explicit don't-weaken-it instruction. (2) Flip-flopping persisted anyway — prompt-only enforcement wasn't reliable enough, so a hard code-level guard was added (`confidenceRank` comparison in `route.ts`: an automated turn can raise confidence or update text at the same confidence, but never silently lower it). (3) A false 0% reading despite the database genuinely holding all 6 categories solid — the categories-read query never checked for a Supabase `error`, so a failed read looked identical to "no categories yet" and silently zeroed the whole progress card; fixed with an explicit error check that fails the request (500) instead of guessing, plus a client-side `everMetCategories` union safety net in `page.tsx` so a category, once shown met, can never visually regress. (4) That same error-check fix surfaced the actual root cause behind all the "flip-flopping" above: `column profile_categories.short_summary does not exist` — the real approved-text column is `ai_summary`, not `short_summary`. This had been silently failing on every request all along (the write path was fine; only the read-back into `categoryMap` was broken), fixed across both `route.ts` and `extract.ts`'s `CurrentCategoryState` type, and cross-checked against the actual migration's column list to rule out any other mismatch. (5) After that fix, the AI's reply still asked a baseline question in the same turn the progress card showed "100% — I know you well enough to get started" — the "nothing left needed" case was a weak trailing clause on a long system-prompt sentence that a small model didn't weight heavily enough against a generic opener; fixed by splitting the system prompt into two fully separate, explicit branches (still-needed vs. already-complete) instead of one prompt with a soft aside.
- A follow-up report of duplicate messages in the transcript was investigated (checked the submit handler for a missing double-submit guard — found `disabled={sending}` already covers it) and confirmed with the founder to be their own intentional double-send across a code-change boundary, not a real bug.

## Deviations from the plan

- **Email confirmation is disabled** (`enable_confirmations = false`, pushed via `supabase config push` from `supabase/config.toml`). This was a dev-testing fix, not a product decision: the founder's real-browser signup attempt hit Supabase's built-in email rate limit (partly because a prior API-level test in this same session had already sent one). Disabling confirmation avoids sending any email at all during this phase, sidestepping the rate limit entirely rather than reaching for a second email vendor (Resend) this early, matching `PLAN.md`'s "one vendor until there's a real reason" stance. **Must be re-enabled before real users can sign up** — right now anyone can create an account with any email address, verified or not. `supabase config push` also synced two unrelated cosmetic settings from the default `config.toml` (MFA TOTP enroll/verify disabled, an `https://127.0.0.1:3000` redirect URL added) — harmless, not cleaned up, since pushing the config file syncs its whole state, not just the one setting that mattered here.
