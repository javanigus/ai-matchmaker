**Cross-cutting fix: onboarding category-pivot bug, found by the founder while testing Phase 9.** Unrelated to Trust & Safety — found while creating a second test account to exercise Block, in `src/app/api/onboarding/chat/route.ts`.
- The founder answered a Religion & Spirituality follow-up with a rich, specific message; the AI's reply kept discussing religion and closed with "Anything else about Religion & Spirituality that you'd like to add?" — while the quick-reply pills shown right below it were Lifestyle's (`"Mostly homebody"`/`"Balanced"`/`"Mostly outgoing"`), and the progress tracker showed Religion & Spirituality as freshly checked off. Text and pills disagreed about what category the turn was even about.
- Root cause, confirmed by tracing the actual code rather than guessing: `focusCategory` (the one category the model is allowed to ask about this turn — the existing, already-hardened fix for three earlier "model picks the wrong remaining category" bugs) is computed once per turn, and both the system prompt *and* the deterministic pills/progress are built from that same value. But on the exact turn a category newly completes and `focusCategory` advances to a brand-new one, the system prompt asked the model to do two things in one message: warmly acknowledge the just-finished category, then cleanly pivot to asking about the new one. A rich, engaged answer about the old category pulled the model's attention back to it instead of pivoting — the pills/progress, computed independently of what the model actually wrote, stayed correct throughout and simply exposed the mismatch. Same underlying weakness as the three previously-fixed bugs (trusting prose to reliably do something structurally important), a new failure shape (regressing to the old topic instead of picking a wrong item from the remaining list).
- Fixed the same way those three were: removed the choice instead of asking more forcefully. Added a snapshot of category state from *before* this turn's own extraction (`preTurnCategoryMap`) to detect exactly this situation (`categoryJustTransitioned`). On a transition turn, the single combined call is replaced with two narrowly-scoped calls: one that acknowledges the just-completed category and is explicitly told not to ask anything, and a second that asks the new category's opening question with **zero prior conversation history** — deliberately isolated, since handing it the old category's context is exactly what let the model regress in the first place. An empty context window has nothing to pull it back to. Non-transition turns (the common case: still probing the same category, or nothing left to ask) are untouched, same single-call path as before.
- Verified for real via a throwaway script that replayed the founder's exact scenario end-to-end (relationship_goals → family → a rich religion answer) against the actual running API route: confirmed the transition triggers correctly (`religion_spirituality:true`, `lifestyle:false` after that turn), pills are Lifestyle's, and — the actual fix under test — the reply text no longer mentions religion at all and instead directly asks the Lifestyle question, matching the pills exactly. 5/5 checks passed.
- **Immediate follow-up, same bug family, caught by the founder testing the fix itself**: on the very next category transition (Lifestyle → Career), the reply read "...preferring relaxed evenings at home... Anything else about Lifestyle that comes to mind? What is the highest level of education you have completed? — High school / Bachelor's degree / Master's degree / Doctorate" — call 1 (acknowledgment) had correctly stopped mentioning the wrong category's *content*, but it was still free to append its own trailing question ("anything else about Lifestyle?") despite being explicitly told not to ask one — a prose instruction, same as everything else in this bug family, not reliably followed. Since call 2 always introduces a real new-category question immediately after regardless, any trailing question from call 1 is structurally always wrong (redundant at best; at worst, per the founder's own catch, "it would have ignored what I typed about Lifestyle" if they'd answered the dangling invite instead of the real new question). Fixed deterministically rather than with stronger wording: `stripTrailingQuestion()` regex-trims a final question-ending clause off call 1's output before concatenating call 2's question, with a generic fallback if the whole acknowledgment turned out to be nothing but a question. Verified for real via a second throwaway script replaying the founder's exact Lifestyle→Career scenario against the live API: the reply now contains exactly one question mark (Career's real question), no mention of "Lifestyle," and correctly asks about education. 5/5 checks passed.

## Deviations from the plan

- **Email confirmation is disabled** (`enable_confirmations = false`, pushed via `supabase config push` from `supabase/config.toml`). This was a dev-testing fix, not a product decision: the founder's real-browser signup attempt hit Supabase's built-in email rate limit (partly because a prior API-level test in this same session had already sent one). Disabling confirmation avoids sending any email at all during this phase, sidestepping the rate limit entirely rather than reaching for a second email vendor (Resend) this early, matching `PLAN.md`'s "one vendor until there's a real reason" stance. **Must be re-enabled before real users can sign up** — right now anyone can create an account with any email address, verified or not. `supabase config push` also synced two unrelated cosmetic settings from the default `config.toml` (MFA TOTP enroll/verify disabled, an `https://127.0.0.1:3000` redirect URL added) — harmless, not cleaned up, since pushing the config file syncs its whole state, not just the one setting that mattered here.
